MikuMotionTools

MikuMotionTools converts motion data between character animation and humanoid robot reinforcement learning (RL). It sits between animation-world motion, such as MMD dances, mocap takes and Blender rigs, and robotics-world motion, which is a robot's joint angles and link poses. It translates in both directions.

  • animation → robot builds reference motions for RL training from a Blender armature.
  • robot → animation shows what a trained policy did, as a character animation.

One data structure holds everything: a Rerun .rrd motion file. Every other module converts into or out of that format.

The hub format#

flowchart TB
  A["<b>Blender armature</b><br/>MMD dance, mocap take"]
  B["<b>ROS 2 .mcap log</b><br/>trained policy rollout"]
  H(["<b>Motion store</b><br/>Rerun .rrd"])
  C["<b>Robot joint angles</b><br/>RL reference motion"]
  D["<b>Character animation</b><br/>VRM rig, rendered video"]

  A -->|"armature_to_motion"| H
  B -->|"robot_log_to_motion"| H
  H -->|"MotionRetargetingIK"| C
  H -->|"motion_to_armature<br/>retarget_armature"| D

  classDef hub fill:#e8eefc,stroke:#3b5bdb,stroke-width:2px;
  class H hub

A converter that writes straight to its destination needs one code path per source and destination pair. Four sources and four destinations then need sixteen paths. A hub format needs eight: one reader and one writer per endpoint. The hub also gives every stage the same viewer, the same field names and the same units.

The hub is not only an interchange file. It is also the record of what happened. The <robot>/ layer holds the joint angles a solve reached and, beside them, the goal it was aiming at. The gap between the robot the joints draw and its goal gizmos is the retargeting error, frame by frame, in one file.

animation → robot robot → animation
Sourcea Blender armature with an animationa ROS 2 .mcap log
Hub writereference/<motion>.rrdreference/<motion>.rrd and <robot>/<motion>.rrd
Hard stepinverse kinematics (IK)forward kinematics (FK), then a rotation transfer
Product<robot>/<motion>.rrd, the one file an RL run readsa keyframed Blender rig, and an .mp4
Entry pointconvert_mocap_to_motion.py, then mikumotion retargetmikumotion import, then convert_motion_to_robot.py

An arrow means that the module at its tail feeds the module at its head. The map shows the principal paths, not every import.

urdf.py, armature_tree.py, math.py, presets.py and mujoco_utils.py import the standard library and numpy alone, so Blender's bundled Python can import them. mujoco_utils.py builds MuJoCo scene XML as text, and the caller compiles it, so the module needs no mujoco of its own. motion_sequence.py is the only module that touches the Rerun read and write API, and the only module that knows the quaternion order difference between Rerun and MotionSequence.

Naming rules#

Conversions are named a_to_b, so an inverse pair reads as one on sight: armature_to_motion against motion_to_armature. Use from_ for constructors, as in RobotModel.from_file(path). Use to_ for a method that converts the object it belongs to, as in robot.to_armature_tree().

Install#

Component Version Needed for
Python3.10 or laterthe library and the command line

The rerun binary arrives with the rerun-sdk package, so the steps below cover it.

Install the library#

git clone https://github.com/T-K-233/MikuMotionTools.git
cd ./MikuMotionTools/
uv pip install -e .
uv sync
uv sync --extra examples
uv sync --extra hf

The examples extra carries the daqp QP solver and the rate limiter that mikumotion retarget imports. Skip it only if you never run an IK solve. The hf extra carries huggingface_hub, which mikumotion push and mikumotion pull need, and the s3 extra carries boto3 for a bucket instead. Skip both on a machine that reads a store it already has. See the dataset remote.

Check the install:

mikumotion list

The command prints one line per motion in data/motions/reference/. An empty store prints nothing.

Install the Blender-side dependency#

Blender runs the scripts in scripts/blender/ with its own bundled Python, not with the environment above. That Python needs rerun-sdk to read and write the motion store. Install it once per Blender version:

<blender>/python/bin/python.exe -m pip install rerun-sdk

Replace <blender> with the Blender install directory. On Linux and macOS the executable is python3.11 rather than python.exe, under the same python/bin/ directory.

Note The Blender scripts add the current working directory to sys.path. Start Blender from the repository root, so that import mikumotion resolves.

Get the assets#

The repository does not carry the robot assets, the Blender project files or the MMD motions. .gitignore excludes data/robots/ for size, and the license of the animation assets does not permit redistribution.

data/robots/<vendor>/<robot>/mjcf/     the MJCF used for FK and IK
data/robots/<vendor>/<robot>/urdf/     the URDF used for geometry and for rigs
data/robots/<vendor>/<robot>/meshes/   the visual meshes
blender-projects/                      the Blender project files

data/motions/MMD-Motion-Sources.md links to the original author of each MMD motion. Internal developers can use the Google Drive mirror.

Converted motions do not come from either place. They come from the dataset remote, which holds the store itself:

mikumotion pull zamuza

A machine that only reads motions needs nothing else: no Blender, no robot asset, and no MMD source. See the dataset remote.

Install the MMD Tools add-on to import MMD models and motions into Blender. The add-on is not needed for mocap, and not needed for the robot → animation direction.

Usage#

MikuMotionTools has two front ends. The mikumotion command line handles everything that runs in a normal Python environment. The scripts in scripts/blender/ handle everything that needs bpy, and Blender runs them.

Both front ends address a motion by name, not by path. The layout of the store decides which stage lands in which file.

Command line#

mikumotion [--root DIR] <command> [ARGS]

--root DIR selects the motion store directory. It defaults to data/motions, so run every command from the repository root.

mikumotion import#

Convert a robot .mcap log into a motion. The command writes both layers, because a log already carries the joint angles that the robot reached. Forward kinematics turns those angles into body poses, and both layers come from the one sequence.

mikumotion import <log.mcap> <robot.xml> <robot.urdf> [--name NAME]
Argument Description
log.mcapROS 2 log with an /odom topic and a /joint_states topic
robot.xmlRobot MJCF, used for forward kinematics
robot.urdfRobot URDF, whose geometry goes into the robot layer
--name NAMEMotion name. Defaults to the .mcap file name

mikumotion retarget#

Solve a robot's joint angles for a motion, by inverse kinematics. The command reads reference/<name>.rrd and writes <robot>/<name>.rrd.

mikumotion retarget <name> <robot.xml> <robot.urdf> <map> [--view]
Argument Description
nameMotion name in the store
robot.xmlTarget robot MJCF, used for the IK solve
robot.urdfTarget robot URDF, whose geometry goes into the robot layer
mapMap name from mikumotion.presets.RETARGET_MAPS, such as ZAMUZA_TO_LITE_PRO
--viewFollow the solve in a passive MuJoCo window, at a quarter of playback speed

The command needs the rest pose of the source rig, stored as <name>_reset. See the rest offset.

Note The command writes <robot>_frames.xml beside the MJCF. That file is the robot plus two sets of marker bodies, which the --view window uses to draw where each link is and where the IK pulls it.

mikumotion view#

Open every layer of a motion in the Rerun viewer.

mikumotion view <name>

The command resolves the paths and hands them to the rerun binary. It runs no conversion.

mikumotion list#

Show the motions in the store, and the robots that each motion is solved for.

mikumotion list [--remote]
Argument Description
--remoteList the dataset remote instead, as motion names and the layers each has

The remote listing reports no frame count. Reading one would mean downloading the file that the listing exists to avoid downloading.

mikumotion push#

Send motions to the dataset remote.

mikumotion push [NAME ...]
Argument Description
NAME ...Motion names. With none, the whole store

mikumotion pull#

Fetch motions from the dataset remote into the store.

mikumotion pull [NAME ...]
Argument Description
NAME ...Motion names. With none, the whole remote

Both commands print the paths that moved, and both take the remote from MIKUMOTION_REMOTE. See the dataset remote.

Blender scripts#

Every script is named convert_<source>_to_<target>.py, the same a_to_b rule the library's functions follow, so the two pipelines read as a chain of file names:

character  ->  mocap  ->  motion  ->  robot
                            |
                            +------->  character
Script Step Arguments after --
convert_character_to_mocap.pyanimation → robot, 1 of 3<preset>
convert_mocap_to_motion.pyanimation → robot, 2 of 3<preset>
convert_motion_to_robot.pyrobot → animation, 2 of 3<motion> <urdf> [--video PATH]
convert_motion_to_character.pyrobot → animation, 3 of 3<motion> <urdf> [--video PATH]

The remaining step of each pipeline is a mikumotion subcommand: retarget finishes animation → robot, and import starts robot → animation.

Note These four run under Blender's own Python, because they need bpy. uv run cannot start them, however much the names read like it — use blender … --python <script> -- as below.

blender ./blender-projects/zamuza.blend --python ./scripts/blender/convert_mocap_to_motion.py -- zamuza
blender --background --python ./scripts/blender/convert_motion_to_robot.py -- lite_pro_tracking <robot.urdf> --video ./renders/robot.mp4
blender ./character.blend --background --python ./scripts/blender/convert_motion_to_character.py -- lite_pro_tracking <robot.urdf> --video ./renders/character.mp4

Both convert_motion_to_* scripts take the robot layer to read from the name attribute of the URDF, and both build the robot's rig through the one blender.motion_to_robot_armature. convert_motion_to_character.py takes the first armature in the .blend file as the target character, which is why it looks for that armature before building the robot's.

Warning Open the character .blend file with convert_motion_to_character.py, not the robot project. The script overwrites the F-curves of every mapped bone on the target armature.

Blender is often built without FFmpeg, and no flag reports whether the encoder is there. The render scripts therefore always write a PNG sequence, then hand it to an external encoder. That encoder is ffmpeg on the path unless MIKUMOTION_FFMPEG names another one. It is a property of the machine rather than of a render, so it is an environment variable and not a flag.

Walkthrough: animation → robot#

flowchart LR
  MMD["character armature<br/>MMD, Mixamo, ActorCore"]
  BL["mocap rig<br/>SMPL keypoint order"]
  RST["reference/&lt;name&gt;_reset.rrd<br/>rest pose"]
  REF["reference/&lt;name&gt;.rrd<br/>body poses"]
  ROB["&lt;robot&gt;/&lt;name&gt;.rrd<br/>joint angles"]
  IK{{"MotionRetargetingIK"}}

  MMD -->|"convert_character_to_mocap.py"| BL
  BL -->|"convert_mocap_to_motion.py"| RST
  BL -->|"convert_mocap_to_motion.py"| REF
  RST --> IK
  REF --> IK
  IK -->|"mikumotion retarget"| ROB

1. Prepare the Blender project. Import the source motion, and set the scene frame rate to the policy update rate:

bpy.context.scene.render.fps = 50

2. Add the helper bones. Add one bone per body part that you want to export, named <smpl_name>.frame, such as pelvis.frame and left_hand.frame. Parent each helper bone to the rig bone that carries that body part.

The helper bone gives the export a stable name and a stable axis convention on a rig whose own bones have neither. armature_to_motion reads the bone that matches <body_name> + ".frame".

3. Add an export preset. Add an entry to MOCAP_RIGS in mikumotion/presets.py:

Key Type Description
armaturestrName of the armature object in the .blend file
scalefloatFactor that converts the rig's units to metres
rotate_zfloatRotation about world Z, in radians, that turns the rig to +X forward
frames(int, int)First and last frame of the animation, inclusive
boneslist[str]Body parts to export, in SMPL keypoint order

Warning Give each body part a distinct name. The store rejects a repeated name, because two bodies would write the same entity path and overwrite each other. A rig with a single spine bone fills one spine slot only.

4. Bake the character's animation onto the rig. Skip this step if the character's own rig carries the .frame helper bones from step 2. The accad and actorcore rigs do, and they export directly.

Any other rig needs the animation transferred first. An MMD model is the usual case. It has hundreds of bones under Japanese names, and local axes that suit MMD rather than an export, so a helper bone on each one is impractical.

Add an entry to CHARACTER_RIGS in mikumotion/presets.py, keyed by the same preset name:

Key Type Description
armaturestrName of the character's armature object in the .blend file
bone_mapdict[str, str]{mocap bone: character bone}, such as {"pelvis": "下半身"}
translation_rootstrThe character bone whose motion places the whole rig in the world

Nothing in the script is specific to one format. A new source, such as Mixamo or ActorCore, is an entry in that table and a bone map beside MMD_TO_ZAMUZA_BONE_MAP. It is never another script.

blender ./blender-projects/zamuza.blend --background --python ./scripts/blender/convert_character_to_mocap.py -- zamuza

The transfer is the same blender.retarget_armature that bakes a robot rig onto a VRM character: both jobs put one rig's motion onto a differently proportioned rig. The script saves the .blend file, so the MMD armature is not needed again.

5. Export the motion.

blender ./blender-projects/zamuza.blend --python ./scripts/blender/convert_mocap_to_motion.py -- zamuza

The script writes two files. reference/zamuza_reset.rrd holds the rig at rest, over two frames. reference/zamuza.rrd holds the animation. The IK solve needs both.

6. Add a retargeting map. Add an entry to RETARGET_MAPS in mikumotion/presets.py, which pairs each source body with a robot link and an orientation cost:

ZAMUZA_TO_LITE_PRO = {
    "pelvis": ("pelvis", 0.5),
    "left_hand": ("left_hand", 0.5),
    "left_shoulder": ("left_shoulder_yaw", 0.1),
    # ...
}

The IK always tracks position at cost 1.0. A high orientation cost, such as 0.5, pins the limb's orientation as well as its position. Use it for the pelvis, the chest, the head, the hands and the feet. A low cost, such as 0.1, lets the IK swing the segment freely and uses the orientation only to steer the elbow or the knee. Use it for the upper and lower arm, and for the upper and lower leg. See task weights and pole targets.

7. Solve the robot's joints.

mikumotion retarget zamuza ./data/robots/berkeley_humanoids/lite_pro/mjcf/lite_pro.xml ./data/robots/berkeley_humanoids/lite_pro/urdf/lite_pro.urdf ZAMUZA_TO_LITE_PRO

A progress bar reports the frames, and the command prints the output path when it finishes. Add --view to watch the solve. Cyan markers show where each link is, and magenta markers show where the IK pulls it.

8. Check the result.

mikumotion view zamuza

Compare the goal gizmos against the robot's links. A goal is what the IK aimed at, so the gap between a gizmo and the link under it is the retargeting error for that frame. Both are in the robot layer, so rerun data/motions/lite_pro/zamuza.rrd shows the comparison on its own. Read the joint-angle plot on the right for steps and for saturation at a joint limit.

A large and constant orientation error on one limb points at the retargeting map. A large error that appears only in fast frames points at the frame rate, or at a pose that the robot's joint limits cannot reach.

9. Share it.

mikumotion push zamuza

The training run reads it from there, and needs no Blender, no MMD source and no robot asset. See the dataset remote.

Walkthrough: robot → animation#

flowchart LR
  LOG["rollout.mcap<br/>/odom + /joint_states"]
  REF["reference/&lt;name&gt;.rrd"]
  ROB["&lt;robot&gt;/&lt;name&gt;.rrd"]
  RIG["robot armature<br/>built from the URDF"]
  CH["VRM character"]
  MP4["renders/*.mp4"]

  LOG -->|"mikumotion import"| REF
  LOG -->|"mikumotion import"| ROB
  ROB -->|"motion_to_armature"| RIG
  RIG -->|"convert_motion_to_robot.py"| MP4
  RIG -->|"retarget_armature"| CH
  CH -->|"convert_motion_to_character.py"| MP4

1. Import the log.

mikumotion import ./data/logs/rollout.mcap ./data/robots/berkeley_humanoids/lite_pro/mjcf/lite_pro.xml ./data/robots/berkeley_humanoids/lite_pro/urdf/lite_pro.urdf --name lite_pro_tracking

The command prints the sequence summary and every file it wrote. A warning names any model joint that the log does not carry. Those joints stay at 0.

2. Check the import.

mikumotion view lite_pro_tracking

The robot moves with its geometry, and the joint-angle plot follows it.

3. Render the robot.

blender --background --python ./scripts/blender/convert_motion_to_robot.py -- lite_pro_tracking ./data/robots/berkeley_humanoids/lite_pro/urdf/lite_pro.urdf --video ./renders/robot.mp4

The script builds the armature from the URDF, imports the visual meshes, keys the motion onto the bones, and renders with a camera that follows the root body.

4. Render the character.

blender ./blender-projects/nai_model.blend --background --python ./scripts/blender/convert_motion_to_character.py -- lite_pro_tracking ./data/robots/berkeley_humanoids/lite_pro/urdf/lite_pro.urdf --video ./renders/character.mp4

The script builds a hidden robot rig without meshes, and keys the motion onto it. It then bakes each VRM humanoid bone from the robot link that carries that segment's world orientation. The bone map is presets.LITE_PRO_TO_VROID_BONE_MAP.

The dataset remote#

A motion is written on one machine and read on several. The workstation that writes it needs Blender, an MMD source and a robot asset. A training run needs none of those: it needs the .rrd files. A deployment target, a colleague, and a run that repeats last month's result all need the same files.

The store is a directory of files, so sharing it needs nothing more than a file transfer. The remote mirrors the layout one for one. A store-relative path, such as reference/zamuza.rrd, addresses the same file on both sides: <root>/reference/zamuza.rrd on disk, and reference/zamuza.rrd in the repository or the bucket.

That mirror is the whole contract. The layout already names every file, so nothing keeps a manifest or an index of what is where. A backend is a class with three methods, and it inherits nothing:

Method Meaning
paths()every file the remote holds, as store-relative posix paths
pull(paths, root)copy those paths down, so each lands at root / path
push(paths, root)copy each root / path up, to the same path

No method knows what a motion is. motion_paths turns a motion name into a list of files, once, for every backend. A push and a pull therefore cannot disagree about which files a motion is, because both directions call the same function. One direction passes it a local listing, the other a remote one.

Where the remote is#

A URI names the remote and its scheme picks the backend.

URI Backend
hf://<owner>/<name>a Hugging Face dataset repository
hf://<owner>/<name>@<revision>that repository at one branch, tag or commit
hf://datasets/<owner>/<name>the same repository, in the Hub's own URI form
s3://<bucket>/<prefix>an S3 bucket, the prefix standing in for the store root

The hf://datasets/... form is the grammar that the hf command line takes, so one URI works with both tools: hf download hf://datasets/your-org/mikumotion-motions fetches the same dataset that mikumotion pull does.

MIKUMOTION_REMOTE holds the URI, so an environment is configured once instead of on every command. A training image sets it in its own environment, and every pull inside that image then needs no argument.

export MIKUMOTION_REMOTE=hf://your-org/mikumotion-motions
$env:MIKUMOTION_REMOTE = "hf://your-org/mikumotion-motions"

A revision pins a read. hf://your-org/mikumotion-motions@v1.2 is one immutable set of motions, which is what a training run needs to stay reproducible after the dataset moves on. A bucket has no revisions, so give each release of an S3 dataset its own prefix instead.

What a name moves#

Both commands address a motion the way every other command does, by name.

mikumotion push zamuza
mikumotion pull zamuza

A name selects every layer whose file has that stem, in whichever layer directory, plus the blueprint of each robot the motion was solved for. Pulling zamuza therefore brings reference/zamuza.rrd, lite_pro/zamuza.rrd and blueprints/lite_pro.rbl, and the motion opens in the viewer with the layout it was written for.

A name never implies another name. mikumotion retarget needs the source rig's rest pose, stored as its own motion, so pull it too before a solve:

mikumotion pull zamuza zamuza_reset

With no name at all, both commands move the whole store. Only .rrd and .rbl files travel. The sources note beside them belongs to git, and the download metadata a pull leaves in <root>/.cache belongs to the machine that pulled.

Transfers are idempotent. On Hugging Face they are also cheap to repeat. A push drops an unchanged file from the commit, and it makes no commit at all when nothing changed. A pull returns the file on disk, without downloading it, when the file and its recorded commit hash both match.

A pull at the start of a training job is therefore mostly metadata, once the store is warm. An S3 transfer has no such check, so it re-sends the bytes.

Reading a motion without a pull#

The Rerun viewer takes more than a path. rerun --help lists an HTTP(S) URL to an .rrd or .rbl file among the inputs it loads. You can therefore open a motion where it sits on a public host, and the viewer pulls down only the parts it needs. That is why the store is a set of plain files addressed by path, and it is what the .rrd hub format was chosen for.

mikumotion view does not do this. It resolves names against the local store, so pull the motion first. The shortcut works for a public dataset only. mikumotion push creates a private repository, and a private file needs a signed URL that the viewer cannot request on its own.

rerun https://huggingface.co/datasets/<owner>/<name>/resolve/main/reference/zamuza.rrd

Hugging Face#

The repository holds the store's own directories, so the dataset is browsable on the Hub and a reader can fetch one motion without cloning the rest.

Each direction is one call to a huggingface_hub bulk helper, given the selected files as allow_patterns, rather than a loop over single files. That is where most of the behaviour comes from, and none of it is written here:

Direction Helper What the helper does
pushHfApi.upload_folderchecks, uploads and commits in parallel; splits a large transfer into several commits; resumes when re-run; drops a file the Hub already holds
pullsnapshot_downloadfetches files concurrently; skips a file whose recorded commit hash still matches; writes the repository's structure into the store

The Hub's docs name upload_folder and snapshot_download as the functions to reach for first, and upload_large_folder is deprecated in favour of upload_folder. Both match allow_patterns with fnmatch, so a motion whose name contains *, ? or [ would select more than itself. Motion names are plain identifiers, and keeping them that way is the reason this is a footnote rather than a bug.

A pull records what it fetched in <root>/.cache/huggingface/. That is what the next pull reads to decide what to skip, and both helpers ignore the directory, so it never travels.

Large files go to Xet storage rather than LFS. Xet splits a file into content-defined chunks and stores each distinct chunk once. That matters more here than it looks. Every <robot>/<motion>.rrd carries its own copy of the robot's geometry, about 9 MB of byte-identical mesh per motion. That copy is the price the store pays for a layer that opens on its own. On the Hub the copies collapse to one, however many motions the dataset holds.

Set HF_XET_HIGH_PERFORMANCE=1 to let a transfer use the whole machine.

A repository that mikumotion push creates is private. The license of an MMD motion does not permit redistribution, and a motion retargeted from one carries that restriction with it. Make a dataset public on the Hub deliberately, once every motion in it allows that.

Authentication is huggingface_hub's own. Set HF_TOKEN, which is what a training image or a CI job should do, or run hf auth login once on a workstation.

S3#

boto3 reads its own credential chain: the environment, the shared credentials file, or the instance role a training node already runs under. A bucket needs nothing else, and the prefix takes the place of the store root.

S3Remote implements the same three methods over list_objects_v2, download_file and upload_file. It has no unchanged-file check, so it moves every file it is given. An ETag is an MD5 for a single-part upload only, which makes it unreliable as a content identity for a file this large. A size alone is too weak to trust.

Neither backend ever sees a credential from MikuMotionTools. Each one asks its own library, which reads the token from wherever that library already keeps it.

Another backend#

A new backend is a class with those three methods, plus one entry in the scheme table of uri_to_remote. It subclasses nothing, so there is no base class to satisfy.

tests/test_motion_remote.py holds one such backend, DirectoryRemote. It meets the contract over a local directory with nothing but shutil, in ten lines. That is the proof that three methods are enough, and the reason the tests need no network.

Rerun's own data platform is the other candidate, and its vocabulary already matches the store's. rerun.catalog.CatalogClient in 0.36 creates and reads datasets. A DatasetEntry exposes segment_ids, register, register_prefix and register_blueprint, and the rerun CLI has a download command for Rerun Hub.

A catalog is a different shape of remote. It registers recordings that live at a URL rather than holding copies of files. A catalog would therefore read what a Hugging Face dataset already serves, instead of replacing it.

The motion format#

A motion is a Rerun .rrd recording. The store holds one directory per pipeline stage and one file per motion, which follows the Rerun dataset convention:

data/motions/
  reference/   <motion>.rrd   body poses as exported, robot-agnostic
  <robot>/     <motion>.rrd   everything one robot needs for that motion
  blueprints/  <robot>.rbl    viewer layout for that robot

A layer is a pipeline stage. A file is one motion segment: a dance, an episode, a take. File names match across layers, so reference/zamuza.rrd and lite_pro/zamuza.rrd are one segment at two stages.

A robot layer is self-contained. It holds that robot's joints, the goal its links track, and its geometry, so a training run or a deployment reads that one file and needs no other. reference/ is provenance: the export as it was, before any robot was chosen.

The in-memory form#

MotionSequence is a plain mutable container. A producer allocates one and fills the arrays in place. For F frames, D joints and B bodies:

Field Shape Unit Description
fpsscalarHzframe rate
joint_namesD—joint names, in the robot's own order
body_namesB—body or link names
joint_positions(F, D)radjoint angles
joint_velocities(F, D)rad/sjoint angular velocities
body_positions(F, B, 3)mlink positions, world frame
body_rotations(F, B, 4)—link rotations, world frame, (qw, qx, qy, qz)
body_linear_velocities(F, B, 3)m/slink linear velocities, world frame
body_angular_velocities(F, B, 3)rad/slink angular velocities, world frame

Every field is world frame, not parent-relative. A consumer therefore needs no kinematic tree to place a body.

Entity paths#

Poses live in a group, one per layer: reference/body says where the exported rig's bodies are, and <robot>/goal says where a robot's links must reach. One function pairs a layer with its group, so the writer, the reader and the viewer layout cannot disagree about it. One writer and one reader serve either group:

/<group>/poses/<name>             Transform3D, one entity per body, one row per frame
/<group>/frames/<name>            a gizmo bound to a coordinate frame, static
/<group>/linear_velocities        Arrows3D, one row per frame, every body an instance
/<group>/angular_velocities       Arrows3D
/reference/body/...               those four, for the exported rig's own bodies
/<robot>/goal/...                 those four, for where that robot's links must reach
/<robot>/body/frames/<link>       a gizmo on every link frame of the joint chain
/<robot>/joint/positions          Scalars, one row per frame, every joint an instance
/<robot>/joint/velocities         Scalars
/<robot>/tf                       Transform3D per joint, plus the root link's placement
/<robot>/tf_static                the URDF's fixed transforms
/<robot>/visual_geometries/...    the URDF's geometry, named by Rerun's URDF loader

Each body gets its own entity, so a body is addressable by name, and its own gizmo, so a 3D view can draw the frame that pose defines. The velocities stay in one batched entity each, one row per frame. A row per body would spend more bytes on Rerun row ids than on the data.

A robot layer's body is not a pose group. It holds the link gizmos and nothing else, because the robot's own poses are the forward kinematics of its joints.

The frame graph#

Every entity that a 3D view draws must name a coordinate frame. An entity with no frame is an orphan. The viewer invents a frame for it, finds no route to the view's root, and draws an error in place of the entity. Scalars are exempt, because the viewer plots them against time.

flowchart TD
  W(("world"))
  W --> RB["<b>reference/body/&lt;name&gt;</b><br/>one frame per exported body<br/>from /reference/body/poses/&lt;name&gt;"]
  W --> RL["<b>lite_pro/pelvis</b><br/>root link placement<br/>from /lite_pro/tf"]
  RL --> J["<b>lite_pro/&lt;link&gt;</b><br/>the URDF joint chain<br/>carries the visual geometry"]
  W --> LB["<b>lite_pro/goal/&lt;link&gt;</b><br/>where that link must reach<br/>from /lite_pro/goal/poses/&lt;link&gt;"]

A frame can have only one parent. A goal therefore names its own frames, <robot>/goal/<link>, because the joint chain in /<robot>/tf already defines a frame named <robot>/<link>.

The layer prefix keeps a reference body apart from a robot link of the same name. It also lets you open two robots in one recording without one overwriting the other's entity paths.

The goal, not the pose reached#

A robot layer stores the goal, and says so in the path: /<robot>/goal/ and not /<robot>/body/. The pose the solve reached is the forward kinematics of the joints in the same file, and /<robot>/tf already draws the robot there, so keeping it would repeat what the file already holds. The goal is recoverable from nothing else: it is the pose the IK aimed at and could not reach.

A goal names the robot's own links, never the source rig's bodies, and its rotation is already carried onto the link's frame convention by the rest offset the solve measured. A tracking reward therefore compares it against the robot directly, and a reader needs no map between the two rigs — for zamuza on lite_pro the vocabularies differ, spine1 against chest, and only the retargeting map in presets.py pairs them.

Joints are never written to reference/, even when the sequence carries them. A joint angle means something for one robot only, so it belongs to that robot's layer.

Reading a motion#

from mikumotion.motion_sequence import MotionStore

store = MotionStore("data/motions")

motion = store.read_reference_motion("zamuza")               # the exported rig's own poses
motion = store.read_robot_motion("zamuza", "lite_pro")       # that robot's joints + its goal

Each call reads one file. read_robot_motion returns the joints the solve reached, and body arrays that are the goal those joints were solved for, under the robot's own link names. That is what a training run tracks, so a training image needs the robot layer and nothing else.

Why several files open as one recording#

Every layer shares application_id = "mikumotion" and recording_id = <motion>. The viewer pools data by those two ids, so several files open as one recording:

rerun data/motions/*/zamuza.rrd data/motions/blueprints/lite_pro.rbl

Each layer also embeds its own blueprint, so any one file opens sensibly alone. Blueprints do not merge, and the last one that the viewer loads wins. Pass blueprints/<robot>.rbl last.

Note Each motion's robot layer carries its own copy of the robot geometry. A shared geometry file would need a different recording id, and Rerun cannot compose a second recording against the motion (rerun-io/rerun#7316).

Conventions#

Axes and units#

The motion format is right-handed, Z up, +X forward, metres, radians and seconds. That matches MuJoCo, URDF and ROS.

Blender rigs are authored +Y forward. convert_mocap_to_motion.py therefore turns each rig about world Z by the rotate_z value of its preset, and scales it to metres by the scale value.

armature_to_motion also cancels the rig's global XY offset. It subtracts the mean X and the mean Y of frame 0 from every frame. A motion therefore starts above the world origin, whatever the rig's placement in the .blend file. It leaves Z alone, so the rig keeps its height above the floor.

Blender bone frames#

A Blender bone carries its own axes, and they are not the axes a motion records. The bone's local +Y runs from its head to its tail, along the bone. Its local +Z is the roll reference, and the bone's roll angle turns +Z and +X about +Y. Its local +X completes the right-handed triple.

A body frame in a motion follows the robot convention instead: +X forward, +Z up. A rig bone therefore cannot serve as a body frame. A thigh bone points down the leg, so its +Y points down the leg, and a hand bone points along the hand. The axes follow the skeleton rather than the world.

The .frame helper bone settles this. Parent one child bone to each rig bone you want to export, and name it <body>.frame. Orient the helper so that its own axes are the axes you want recorded. armature_to_motion then reads the helper and never the rig bone: bone_names holds the body names, and the function appends .frame to each one.

For each helper, armature_to_motion records two things. The position is the helper's head. The rotation is the helper's pose matrix. Both pass through armature.matrix_world, so a rig that is moved or turned as an object exports the same motion.

Two consequences follow. Put the helper's head exactly where the body's origin belongs, because the head is the position that is recorded, and the helper's length changes nothing. Then set the orientation in two moves: where you point the helper fixes its +Y and therefore two of its three axes, and its roll fixes the last one.

Note The robot side needs no helper bones. robot_model_to_armature builds one bone per URDF link, and motion_to_armature drives those bones through matrix_basis, so the link frames come from the URDF rather than from a bone's head-to-tail axis.

Quaternion order#

Four libraries in this pipeline disagree about quaternion order:

Context Order
MotionSequence.body_rotations(w, x, y, z)
Rerun Transform3D(x, y, z, w)
ROS geometry_msgs/Quaternion(x, y, z, w)
MuJoCo xquat and qpos(w, x, y, z)
Blender mathutils.Quaternion(w, x, y, z)

Two modules hold every conversion. motion_sequence.py converts on the Rerun boundary, with quat_to_xyzw and quat_to_wxyz. mcap_io.py converts on the ROS boundary, and normalizes the logged quaternion, because a logged value is not guaranteed to be unit length.

Quaternion products follow the Hamilton convention. quat_mul(a, b) is the rotation matrix product $R_a R_b$, so a world-frame rotation post-multiplies.

Velocities#

Every producer calls fill_body_velocities instead of differencing poses itself. The linear part is a plain finite difference:

$$ v_t \;=\; \frac{p_t - p_{t-1}}{\Delta t}, \qquad \Delta t = \frac{1}{\mathrm{fps}} $$

The angular part has two traps. First, Euler-angle rates are not an angular velocity, so the rotation between two consecutive frames has to produce it. Write that step as a quaternion:

$$ \Delta q_t \;=\; q_t \otimes q_{t-1}^{*} $$

Second, that step must go the short way round. A quaternion and its negation are the same rotation, and a sign flip between frames reads as a near-full turn. Unflipped, it spikes the velocity at $2\pi\,\mathrm{fps}$. The fix negates any step with a negative real part. With $\Delta q_t = (w, \mathbf{u})$ and $s = \lVert \mathbf{u} \rVert$:

$$ \omega_t \;=\; \frac{\mathbf{u}}{\Delta t}\cdot\frac{2\,\mathrm{atan2}(s, w)}{s} $$

The scale factor $2\,\mathrm{atan2}(s, w) / s$ tends to 2 as the step vanishes, so the implementation uses 2 where $s < 10^{-12}$. Frame 0 keeps its zeros, because there is no earlier pose to difference against.

The IK solve differences its own joint angles the same way, because mink integrates qpos and leaves qvel at zero. mj_objectVelocity would report every body as motionless.

Frame rate#

Match the frame rate of the motion to the policy update rate of the training environment, usually 50 Hz. A mismatch forces the training run to interpolate every frame, which costs time and blurs fast contact events. convert_mocap_to_motion.py asserts that the Blender scene is 50 fps. mcap_io.py infers the rate from the median sample period of the log, which ignores the gaps that dropped messages leave.

Body naming#

Name generic bodies after the SMPL-X joint names. One name then means one body part across every rig and every retargeting map. Robot layers keep the robot's own link names instead, because those must match the URDF.

Theory: animation → robot#

The problem is a mapping between two skeletons that share a topology but not their proportions, their axis conventions or their degrees of freedom. A character's arm is a chain of ball joints. A robot's arm is a chain of 1-DOF hinges with hard limits. No rotation copy can satisfy both, so this direction solves an optimization problem instead.

The direction runs in two stages. Stage 1 reads the Blender armature into the hub. Stage 2 solves the robot's joint angles by inverse kinematics.

Stage 1: read the armature#

For each frame $t$ and each helper bone $b$, armature_to_motion reads the bone's world pose from Blender:

$$ T_b(t) \;=\; M_{\text{world}} \, P_b(t) $$

$M_{\text{world}}$ is the armature object's matrix_world, and $P_b(t)$ is the pose bone's matrix. A pose bone's own matrix is in armature space, so it is a world pose only when the armature object sits at the origin unrotated. The product makes a placed or turned rig export the same motion.

The body position is the bone's head, not the centre of its matrix:

$$ p_b(t) \;=\; M_{\text{world}}\, h_b(t), \qquad R_b(t) \;=\; \mathrm{rot}\big(T_b(t)\big) $$

convert_mocap_to_motion.py then applies the preset: it scales the positions to metres, and turns every world-frame field about Z by rotate_z. It runs the export twice, once with the armature forced to REST and once with it in POSE, which produces <name>_reset and <name>.

A rig has no joint angles, so this stage writes body poses only. Joint angles belong to a robot, and stage 2 produces them.

Stage 2: the IK problem#

The robot configuration is

$$ q \;=\; (\,p_{\text{base}},\; q_{\text{base}},\; \theta\,) \;\in\; \mathbb{R}^3 \times S^3 \times \mathbb{R}^{n} $$

MuJoCo stores it as qpos, where a floating base occupies the first 7 entries and the $n$ hinge angles follow. Forward kinematics gives each link's world pose $T_i(q) \in SE(3)$.

A description written for a fixed-base simulation pins its root link, which leaves the IK unable to place the robot in the world. MotionRetargetingIK therefore compiles the model through MjSpec and adds a free joint to the root body if it has none.

The retargeting map lists the pairs to track. For a pair (source body $s$, robot link $i$) with orientation cost $w_i$, the target pose at frame $t$ is

$$ p^{*}_i(t) \;=\; p_s(t), \qquad R^{*}_i(t) \;=\; \underbrace{R_s(t)\, R_s^{\text{rest}\,\top}}_{\Delta R_s(t)} \; R_i^{0} \tag{1} $$

$R_s^{\text{rest}}$ is the source bone's rotation in the rig's rest pose, and $R_i^{0}$ is the link's rotation at the robot's zero configuration. The next section explains why.

The rest offset#

A mocap bone and the link that it drives disagree about which way their axes point. The zamuza foot bone and the lite_pro foot link sit 90 degrees apart with both rigs at rest. Aiming the IK at the source's absolute orientation therefore twists the robot's foot by that much for the whole motion.

rest_offsets measures the constant part once, as a quaternion:

$$ q_{\text{off}} \;=\; \big(q_s^{\text{rest}}\big)^{*} \otimes\, q_i^{0} \tag{2} $$

The per-frame target is then a single product, which is equation (1) written in quaternion form and regrouped:

$$ q^{*}_i(t) \;=\; q_s(t) \otimes q_{\text{off}} \;=\; \underbrace{q_s(t) \otimes \big(q_s^{\text{rest}}\big)^{*}}_{\Delta q_s(t)} \otimes\, q_i^{0} \tag{3} $$

Equation (3) is one rule: take the source bone's world-frame rotation away from its own rest pose, and apply it to the link's rotation at the robot's zero pose. The rule cancels both rigs' axis conventions, so nobody has to tune an offset by hand.

Note The same rule drives the other direction. desired_pose_matrix in blender.py applies the source bone's world-frame rest delta to the target bone's rest orientation. Both directions compose the delta on the left, in world frame. See the rotation transfer.

The solve needs reference/<name>_reset.rrd for $q_s^{\text{rest}}$, and stops with an assertion if that file is missing.

The differential IK step#

The solve is a differential IK, driven by mink. Each iteration linearizes the tasks about the current configuration and solves one quadratic program (QP) for a configuration displacement $\Delta q$ in the tangent space:

$$ \min_{\Delta q}\;\; \sum_{k}\Big\lVert W_k \big( J_k(q)\,\Delta q + e_k(q) \big) \Big\rVert^2 \;+\; \Big( \lambda + \textstyle\sum_k \mu_k \Big) \lVert \Delta q \rVert^2 \qquad \text{subject to} \quad G\,\Delta q \le h \tag{4} $$

The terms are:

Term Value here Meaning
$e_k(q)$—task error. For a frame task it is the body twist $\log\!\big(T_i(q)^{-1} T^{*}_i\big) \in \mathbb{R}^6$
$J_k(q)$—task Jacobian, $\partial e_k / \partial q$. For a frame task it has shape $6 \times n_v$
$W_k$$\mathrm{diag}(1,1,1,w_i,w_i,w_i)$task weights: position cost 1.0, orientation cost $w_i$ from the map
$\lambda$DAMPING = 0.5Tikhonov damping on every DOF, the floating base included
$\mu_k$$\nu \lVert W_k e_k \rVert^2$, $\nu =$ lm_damping = 1.0Levenberg–Marquardt damping, which grows with the task error
$G\,\Delta q \le h$ConfigurationLimit$q \ominus q_{\min} \le \Delta q \le q_{\max} \ominus q$, the robot's joint limits

The solver is daqp, through qpsolvers. mink then returns $v = \Delta q / \mathrm{d}t$ and integrate_inplace(v, dt) applies $q \leftarrow q \oplus v\,\mathrm{d}t$, so the timestep cancels. ConfigurationLimit ignores its dt argument, so the value of model.opt.timestep does not affect the result.

The two damping terms do different jobs. $\lambda$ is constant and bounds the step everywhere. $\mu_k$ grows with the square of the task error. A task far from its target therefore takes a short, safe step, and a task near its target is barely damped.

Task weights and pole targets#

A humanoid IK problem is redundant. Many arm configurations put the hand in one place, and they differ in where the elbow points. Position tasks on the hands and feet alone therefore leave the elbows and knees free to flip from one solution to another between frames.

ZAMUZA_TO_LITE_PRO fixes that with two grades of orientation cost:

Bodies Orientation cost Role
pelvis, chest, head, hands, feet0.5pin the pose. A hand's roll and a foot's yaw carry meaning
upper and lower arm, upper and lower leg0.1pole target. Steer the elbow and the knee without fighting the end effector

The low cost is the point of the design. Weights enter the objective squared. A segment's orientation task at cost 0.1 therefore contributes one twenty-fifth of a 0.5 task, and one hundredth of a position task. It picks one branch out of the redundant set without pulling the hand off its target.

The posture regularizer#

A straight limb is a kinematic singularity. Where the knee angle reaches zero, two of the leg's rotation axes line up. The Jacobian loses rank there, so the QP has no well-conditioned direction to bend the knee in.

MotionRetargetingIK adds a PostureTask at cost 0.1, whose target holds every joint at its model default except the knees and the elbows:

$$ \theta^{\text{ref}}_j \;=\; \begin{cases} +0.2\ \text{rad} & \text{if the joint name contains } \texttt{knee} \\ -0.2\ \text{rad} & \text{if the joint name contains } \texttt{elbow} \\ \theta^{\text{default}}_j & \text{otherwise} \end{cases} \tag{5} $$

The same posture is also the initial configuration, so frame 0 starts off the singularity as well as ending off it. At cost 0.1 the task loses to every frame task, so it changes the result only inside the null space that the frame tasks leave free.

The per-frame loop#

flowchart TB
  S["frame t: set every task target<br/>position p_s(t), orientation q_s(t) ⊗ q_off"]
  E0["measure the total task error"]
  Q["solve the QP of equation (4)<br/>then integrate q ← q ⊕ Δq"]
  C{"error decrease<br/>&gt; 1e-4 ?"}
  IT{"iterations<br/>&lt; 40 ?"}
  W["mj_forward, then record<br/>qpos[7:] and every tracked link pose"]

  S --> E0 --> Q --> C
  C -->|"yes"| IT
  IT -->|"yes"| Q
  IT -->|"no"| W
  C -->|"no"| W
  W -->|"next frame"| S

The loop stops when one iteration improves the combined error by less than $10^{-4}$, or after 40 iterations. It prints a warning when it hits the iteration cap.

Warm starting is what makes the solve cheap. Frame $t+1$ begins from the configuration that frame $t$ ended at, and consecutive frames of a 50 Hz motion are close, so most frames converge in a few iterations.

What the solve writes#

The solve records the joint angles from qpos[7:], and the target it aimed each tracked link at — the source pose carried onto that link's frame convention — as the goal. It differences the joint angles for the joint velocities, and calls fill_body_velocities on the goal, because mink integrates qpos and leaves qvel at zero.

write_robot_motion stores that as <robot>/<name>.rrd: the joints, the goal, and the root link's reached pose as the placement that puts the robot in the world. The poses the other links reached are not stored, because they are the forward kinematics of the joints beside them. The reference layer stays untouched.

Theory: robot → animation#

This direction has no optimization. A log already carries the joint angles that the robot reached, so forward kinematics is enough to produce every link pose. The work is in the bookkeeping: three coordinate conventions, three rest poses, and one rig whose bone axes match nothing.

The direction runs in three stages. Stage 1 turns a log into a motion. Stage 2 plays that motion on the robot's own rig. Stage 3 transfers the robot's rig onto a character rig.

Stage 1: forward kinematics#

read_robot_log decodes two ROS 2 topics from the .mcap file and aligns them by log timestamp:

Topic Message Carries
/odomnav_msgs/msg/Odometrythe floating-base pose and twist, in world
/joint_statessensor_msgs/msg/JointStatethe joint angles and joint velocities

Timestamps that appear on one topic only are dropped, and the reader reports how many. The frame rate comes from the median sample period, so the gaps that dropped messages leave do not pull it down. A mean would fold them in.

robot_log_to_motion then reindexes the logged joint angles into MJCF joint order, and runs mj_kinematics once per frame. The lite_pro MJCF has no floating base: pelvis is a fixed root at the world origin. Forward kinematics on the logged angles therefore gives each body's pose relative to the model's root frame, not in the world. The logged base pose is composed on top:

$$ W_b(t) \;=\; T_{\text{base}}(t)\; F_{\text{pelvis}}\big(\theta(t)\big)^{-1}\; F_b\big(\theta(t)\big) \tag{6} $$

$F_{\text{pelvis}}$ is the identity when the MJCF puts its root body at the origin, so equation (6) reduces to $W_b(t) = T_{\text{base}}(t)\, F_b(\theta(t))$. The general form stays correct if a future MJCF places the root away from the origin, which is why the code keeps it.

The MJCF body frames match the URDF link frames, so the resulting motion can drive an armature built from the same URDF. Stage 2 relies on that.

mikumotion import writes both layers from this one sequence. The poses are the export, and the logged joint angles are the solve, so no IK runs.

Stage 2: play a motion on the robot's rig#

robot_model_to_armature builds the rig from the parsed URDF. Each link becomes one bone, with its head at the link origin. Each link's visual mesh is imported, placed at the link frame times the visual's own <origin>, and parented to the matching bone with the transform kept.

The rest placement of a link is the product of the joint origins along its chain:

$$ \mathrm{Rest}_i \;=\; \prod_{j \in \text{chain}(i)} L_j, \qquad L_j = \begin{bmatrix} R(\text{rpy}_j) & \text{xyz}_j \\ 0 & 1 \end{bmatrix} \tag{7} $$

URDF rpy is a fixed-axis rotation: roll about X, then pitch about Y, then yaw about Z, each about the fixed parent axes. The matrix is therefore $R = R_z(\text{yaw})\,R_y(\text{pitch})\,R_x(\text{roll})$, and the quaternion is the Hamilton product $q_z \otimes q_y \otimes q_x$.

Warning A bone's own orientation points head to tail, and does not match its link frame. build_armature gives every bone the same 0.05 m length, because a URDF says nothing about where a bone should point. Never read a link frame off a bone's orientation. Read it from equation (7).

motion_to_armature computes the world-space delta of each driven link:

$$ \Delta_i(t) \;=\; M_i(t)\, \mathrm{Rest}_i^{-1} \tag{8} $$

$M_i(t)$ is the link's world pose from the motion. Blender does not accept a world pose on a pose bone, so the delta has to become a matrix_basis. Blender composes a bone's pose as

$$ \mathrm{Pose}_i \;=\; \mathrm{Pose}_{\text{parent}}\; \big(\mathrm{Bone}^{\text{rest}}_{\text{parent}}\big)^{-1}\, \mathrm{Bone}^{\text{rest}}_i \; \mathrm{Basis}_i \tag{9} $$

Require every driven bone to reach $\mathrm{Pose}_i = \Delta_i\, \mathrm{Bone}^{\text{rest}}_i$, substitute the same requirement for the parent, and equation (9) solves for the basis:

$$ \mathrm{Basis}_i \;=\; \big(\mathrm{Bone}^{\text{rest}}_i\big)^{-1}\; \Delta_{\text{parent}}^{-1}\; \Delta_i\; \mathrm{Bone}^{\text{rest}}_i \tag{10} $$

Equation (10) is exact. It merges no ball joints and approximates nothing, and each bone's basis depends on the motion and the rest pose alone. No bone needs the depsgraph to be re-evaluated before the next bone is posed, which is what keeps a long sequence fast. A mesh parented with the transform kept then lands exactly at $M_i(t)$.

motion_to_armature keyframes location and rotation_quaternion on each driven bone, and sets the scene frame rate and frame range from the motion.

Stage 3: robot rig to character rig#

A robot rig and a character rig share a topology and a rest pose, but not their proportions and not their local bone axes. retarget_armature therefore transfers rotation only, plus one translation on the root.

For each mapped pair (source bone $s$, target bone $b$), all rotations in world frame:

$$ R_b^{\text{desired}}(t) \;=\; \underbrace{R_s^{\text{pose}}(t)\, \big(R_s^{\text{rest}}\big)^{-1}}_{\Delta R_s(t)}\; R_b^{\text{rest}} \tag{11} $$

This is the same rule as equation (1), in the other direction. Cancelling the source's own rest orientation is what makes it work between rigs that share a rest pose but not their bone axes. A URDF robot's link frames against a VRM's head-to-tail bones are such a pair.

Caution Do not map through the rest orientations instead, as $R_b^{\text{rest}} \big(R_s^{\text{rest}}\big)^{-1} R_s^{\text{pose}}$. That form conjugates the delta rather than composing it on the left, and it mangles such a pair in silence. The character still moves, so the error reads as a bad bone map rather than as bad math.

Three details make the transfer hold up:

  1. Depth order. retarget_frame poses the mapped bones in order of their depth in the target armature. A bone reads its parent's current world matrix, so the parent must already carry its own pose. Blender needs a view_layer.update() between bones for that reason, unlike stage 2.
  1. A clean slate per frame. retarget_frame resets each mapped bone to zero location, identity rotation and unit scale before it poses the bone. A stale channel therefore cannot leak into the frame.
  1. Renormalization. A chain of matrix products drifts away from orthonormal, and Blender reads the drift as scale or shear on the bone. rot3_orthonormalized renormalizes at every step.

The root also takes a world position, which follows the source root with a constant offset:

$$ p_b^{\text{root}}(t) \;=\; p_s^{\text{root}}(t) \;+\; c, \qquad c \;=\; p_b^{\text{root,rest}} - p_s^{\text{root}}(t_0) \tag{12} $$

The offset $c$ is measured once, at the first baked frame, so the two rigs line up there. Deriving the position from the target's rest pose each frame instead would turn the target's rest hip offset by the root's rotation. The character then sinks through the floor as soon as the root turns far, when it lies prone for example.

Chains against ball joints#

The robot models each 3-DOF articulation as a chain of 1-DOF links. A VRM humanoid models the same articulation as one ball bone. The accumulated world orientation of the whole chain sits on its last link, so that link is what the bone map names.

LITE_PRO_TO_VROID_BONE_MAP follows that rule throughout:

VRM bone lite_pro link Why
J_Bip_C_Spine, _Chest, _UpperChestwaist_yaw, waist_roll, chestthe torso chain, in order
J_Bip_*_UpperArm*_shoulder_yawthe last of three shoulder links
J_Bip_*_Shoulder—unmapped. UpperArm already carries the whole shoulder
J_Bip_*_UpperLeg*_hip_yawthe last of three hip links
J_Bip_*_Foot*_footthe last of the ankle links
J_Bip_*_<finger>1..3*_finger<n>_j1..j3the robot's fourth finger joint has no VRM phalanx

A robot finger has four joints and a VRM finger has three phalanges, so j4 is dropped. The finger index follows the robot's own numbering, where finger1 is the thumb, nearest the wrist, and finger5 is the little finger.
